# Static TLS for libbbgpu.so and a fresh GCC profile — 8 November 2026

## Static TLS

`__tls_get_addr` was ~2% of the draw thread's samples at the Shrine (plus its PLT stub), spread
over a dozen `thread_local`s: `CommandRecorder::Publish`, `DrawPhase` marks, `SotcStats::OptOff`,
`ImageInfo`, and the texture cache lock's owner token on every hold. A shared library's
`thread_local`s use the general-dynamic TLS model, a call per access. `bb-probe` links
`libbbgpu.so` directly (no `dlopen`), so on Linux the library is now compiled with
`-ftls-model=initial-exec`: each access is one `%fs`-relative load. The library carries the
`STATIC_TLS` flag and no `__tls_get_addr` calls remain. Each thread now gets the library's 208 KiB
TLS block when it is created instead of on first use.

## Fresh profile

The texture cache header change (c58094f) shifted source locations in every file including it, so
the old profile no longer applied to 628 functions. The profile was retrained from the current tree
with the instrumented build (`BB_PGO=generate`, LTO, GCC 16.2.1), the same two sessions as before
but through the isolated Shrine harness: 140 s with frame generation off (20.6 FPS instrumented)
and 110 s with FSR 3 frame generation (18.0 FPS), 9 periodic profile writes, both correctness gates
passed. The use build (same directory, so the profile file names match) reports no profile
mismatches. The profile is machine- and path-specific and stays outside the repository.

## Profile of the new renderer (40 s `perf`, 5× denser sampling than before)

Draw thread self time: `BackLoop` 8.9% (81% of it the wait-for-work spin, liverpool.cpp:246),
`BindTextures` 7.6% (was 12%; the samples right after `BatchLock()` fell from ~8.8% to ~2.9% of
the thread, and the new fast path has no locked instruction), `ExecuteBackOp` 3.4%, `BindBuffers`
3.4%, `AccessBuffer` 2.8%, `BpeHeapGuard::Read` 2.8% (header reads of the readback heap walk),
`ResetBindings` 2.1%. `memcpy`'s bulk loop is ~13% in all: ~5% guest-buffer uploads
(`SynchronizeMemory` → `CopySparseMemory`, ~3-7 MB per frame), ~1.6% `ExecuteReplicateShaderHLE`,
~2% per-draw structure copies, the rest from callers without frame pointers.

At a steady 60 FPS without a profiler the game log reports, per frame: draw thread busy 14.2 ms,
command parse 10.9 ms, and the command processor waiting for the draw thread once per second. The
draw thread is the longest stage but is idle ~2.5 ms of each 16.7 ms frame; the remaining frame
time is hand-off bubbles across guest → command processor → draw thread → recorder → GPU. Every
remaining single draw-thread item is 1–3%, at or below what an 8-run batch can resolve.
